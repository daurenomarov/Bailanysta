# Bailanysta

Bailanysta — responsive MVP социальной сети: пользователи читают общую ленту, открывают профили и публикуют записи через собственный backend API.

## Возможности

- Лента публикаций и профили пользователей с SPA-навигацией.
- Создание и редактирование собственных публикаций.
- Лайки и комментарии.
- Поиск по тексту и хэштегам.
- Светлая/тёмная тема с сохранением выбора в `localStorage`.
- Loading skeleton, empty/error-состояния и адаптивный интерфейс.
- REST API с валидацией, корректными status codes и seed-данными.

## Скриншоты

Скриншоты будут добавлены после первого публичного deployment.

## Технологии и причины выбора

- **React + React Router + Vite + TypeScript** — небольшой современный SPA-стек с быстрым dev-сервером и строгой типизацией.
- **Express + TypeScript** — простой собственный API в том же репозитории, без дублирования инструментов.
- **JSON-файл** — не требует отдельной БД и позволяет сразу проверить MVP. Для production с несколькими инстансами его следует заменить на PostgreSQL.
- **Node test runner + ESLint** — тестирование критического API без тяжёлой тестовой инфраструктуры и единые проверки качества.

## Архитектура

```text
src/                 React-приложение
  components/        переиспользуемые UI-компоненты
  hooks/             загрузка и состояние публикаций
  pages/             лента и профиль
server/              Express API, seed и файловое хранилище
tests/               интеграционные тесты API
data/db.json          runtime-данные (создаются автоматически, не коммитятся)
```

Frontend обращается только к `/api`. В development Vite проксирует запросы на Express; в production Express раздаёт собранный SPA и API с одного origin.

## Установка и локальный запуск

Нужен Node.js 22+ и npm.

```bash
npm install
cp .env.example .env
npm run dev
```

Откройте `http://localhost:5173/posts` (профиль — `/profile`). API работает на `http://localhost:3001`. Отдельный запуск возможен командами `npm run dev:server` и `npm run dev:client`.

### Переменные окружения

| Имя | Обязательно | Описание |
| --- | --- | --- |
| `PORT` | нет | Порт production/API-сервера, по умолчанию `3001` |
| `VITE_API_URL` | нет | Origin API, если frontend и backend размещены отдельно; локально оставьте пустым |

Секреты приложению не требуются. `.env` исключён из Git.

## Проверка и production build

```bash
npm run typecheck
npm run lint
npm test
npm run build
npm start
```

После build команда `npm start` запускает единый Express-сервер: приложение доступно на `http://localhost:3001/posts`, профиль — на `http://localhost:3001/profile`, API — на том же origin по `/api/*`. `vite preview` для production не используется, поскольку он не запускает Express API.

## Процесс проектирования и разработки

Работа началась с основного flow: API-контракты и seed → лента → профиль и создание поста → состояния интерфейса → бонусные интеракции. Компоненты делились по пользовательской ответственности, а API и хранение отделены от HTTP-маршрутов. Интеграционные тесты проверяют не внутреннюю реализацию, а реальные HTTP-запросы.

Уникальный для этого MVP подход — единый deployable-сервис: один процесс обслуживает SPA и API, поэтому CORS и отдельная синхронизация deployments не нужны. Progressive enhancement бонусов построен вокруг одной карточки поста, сохраняя интерфейс компактным.

## Компромиссы и известные ограничения

- Авторизация не входит в MVP: текущий пользователь фиксирован как `u1`; действия нельзя считать защищёнными от злоумышленника.
- JSON-хранилище удобно локально, но не предназначено для конкурентной записи, горизонтального масштабирования и эфемерных файловых систем.
- Подписки, уведомления и AI-генерация не реализованы: приоритет отдан завершённости основного flow и функциям постов без внешних ключей.
- Пагинации и удаления публикаций пока нет.
- Приложение использует системные шрифты и не передаёт данные во внешние API.

## Deployment

Проект подготовлен для Render через `render.yaml`:

1. Опубликуйте код в публичном GitHub-репозитории.
2. В Render выберите **New → Blueprint** и подключите репозиторий.
3. Проверьте health endpoint `/api/health` после deployment.

На бесплатном Render локальный файл может сбрасываться при redeploy/restart. Для устойчивого production-хранения подключите PostgreSQL и persistent disk. Фактический deployment не выполнялся без разрешения владельца репозитория.
